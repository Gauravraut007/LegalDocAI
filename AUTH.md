# AUTH.md — Identity & JWT Contract

Django is the identity source of truth. FastAPI **never** touches the user
table; it only verifies short-lived JWTs that Django mints.

## 1. Algorithms & Keys

| Setting              | Value                                           |
|----------------------|-------------------------------------------------|
| Algorithm            | `HS256` (`JWT_ALGORITHM`)                       |
| Signing key          | env `JWT_SIGNING_KEY` — shared, ≥ 64 bytes      |
| Issuer (`iss`)       | `django-service` (env `JWT_ISSUER`)             |
| Access TTL           | 15 min (`JWT_ACCESS_TOKEN_EXPIRE_MINUTES`)      |
| Refresh TTL          | 7 days (`JWT_REFRESH_TOKEN_EXPIRE_DAYS`)        |
| Rotate refresh       | Yes (old refresh blacklisted on use)            |
| Blacklist on logout  | Yes (`POST /api/v1/auth/logout`)                |

Both services must read `JWT_SIGNING_KEY` from the same environment value.
The Docker compose `env_file: .env` ensures this. **Never commit the key.**

## 2. Claims (access token)

Generated by `apps.users.serializers.LDIPTokenObtainPairSerializer`:

```json
{
  "iss": "django-service",
  "exp": 1730000000,
  "iat": 1729999100,
  "jti": "...",
  "token_type": "access",
  "user_id": "8d6b...-uuid",
  "email": "alice@example.com",
  "is_staff": false,
  "workspace_ids": ["uuid", "uuid"]
}
```

`workspace_ids` is computed from `WorkspaceMember` at token-issue time. The
client is responsible for re-logging-in (or refreshing) after workspace
membership changes — the API surfaces a hint in the
`/api/v1/invitations/accept/{token}/` response.

FastAPI verifies and enforces:
- `iss == "django-service"`
- `exp` not expired
- All required claims present
- `user_id` and every `workspace_ids[i]` parse as UUID
- Document access: `owner_user_id == user.user_id` **OR**
  `workspace_id ∈ user.workspace_ids` **OR** `is_staff`.

## 3. Endpoints

All under `/api/v1/auth/`:

| Method | Path                        | Notes                                          |
|--------|-----------------------------|------------------------------------------------|
| POST   | `register`                  | Creates user + default personal workspace      |
| POST   | `login`                     | `{access, refresh}`. 5/min/IP throttle         |
| POST   | `token/refresh`             | Returns new access (refresh rotated)           |
| POST   | `logout`                    | Body `{refresh}` — blacklisted                 |
| GET    | `me`                        | Authenticated profile                          |
| PATCH  | `me`                        | Update `full_name`, `avatar`                   |
| POST   | `password/change`           | Authenticated; verifies `current_password`     |
| POST   | `password/reset/request`    | Always returns 202 (no account enumeration)    |
| POST   | `password/reset/confirm`    | `{token, new_password}`; token has 1h TTL      |

## 4. Password policy

`AUTH_PASSWORD_VALIDATORS`:
- Min length 12.
- Common-password check (Django built-in).
- Numeric-only rejected.
- Similarity to user attributes rejected.
- `apps.users.validators.ComplexityValidator`: requires upper, lower, digit,
  symbol.

## 5. Throttling

| Scope             | Rate      | Class                                           |
|-------------------|-----------|-------------------------------------------------|
| Anonymous         | 20/min    | `AnonRateThrottle`                              |
| Authenticated     | 120/min   | `UserRateThrottle`                              |
| `login`           | 5/min     | `apps.users.throttling.LoginRateThrottle`       |
| `register`        | 10/min    | `RegisterRateThrottle`                          |
| `password_reset`  | 5/min     | `PasswordResetRateThrottle`                     |

FastAPI applies an additional Redis token-bucket on chat endpoints
(`app.security.rate_limit.chat_rate_limit`).

## 6. Key rotation

1. Generate the new key.
2. Deploy a release with `JWT_SIGNING_KEY_NEXT` populated; FastAPI accepts
   either current or next during the rotation window (extension point in
   `app.security.jwt`; default verifies a single key).
3. Promote `JWT_SIGNING_KEY = JWT_SIGNING_KEY_NEXT`; clear the next slot.
4. All access tokens minted before the swap will fail verification when they
   reach 15 min TTL → clients seamlessly fall back to refresh, which is also
   re-signed under the new key on rotation. Refresh tokens older than the
   refresh-TTL window are forced to login again.

If a leak is suspected, **immediately rotate** the key and call
`token_blacklist` cleanup on Django to flush long-lived refresh tokens.

## 7. WebSocket auth

WebSocket endpoints accept the access token via:
1. `?token=<JWT>` query parameter (preferred, browser-friendly).
2. `Sec-WebSocket-Protocol: bearer, <JWT>` (sub-protocol negotiation).
3. `Authorization: Bearer <JWT>` HTTP header.

Implemented by `common.channels_auth.JWTAuthMiddleware`. On invalid /
missing token the consumer rejects the connection with close code `4401`.
